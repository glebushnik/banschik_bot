# banschik_bot

Бот для групп Telegram: сохраняет переписку локально, ищет по ней через FAISS
и отвечает только на явное упоминание `@имя_бота`. LLM вызывается через
OpenRouter или другой OpenAI-совместимый API. Эмбеддинги считаются локально на CPU.

## Возможности

- SQLite: сообщения, подписи к медиа, авторы, даты, темы, исходные метаданные Telegram.
- Фоновое разбиение сообщений на перекрывающиеся чанки с проверкой длины токенизатором.
- Мультиязычная quantized ONNX-модель `multilingual-e5-small`, 384 измерения.
- Отдельный FAISS-индекс для каждой группы; модель не может выбрать чужую группу.
- Недавняя переписка и найденные фрагменты передаются модели как контекст.
- Инструменты `search_chat` и `web_search`, которые модель вызывает самостоятельно.
- Локальный SearXNG для веб-поиска без платного поискового API.
- Редактируемый системный промпт: дружелюбно, по делу, без смайликов и эмодзи.
- Ночной cron-бэкап SQLite и FAISS, проверка контрольных сумм, восстановление.
- Сохранённые очередь ответов и Telegram offset переживают перезапуск.

## Быстрый запуск через Docker Compose

Нужны Docker Engine с Compose и доступ к Telegram, OpenRouter, Hugging Face
и поисковым системам. Входящий публичный порт и домен для бота не нужны: используется long polling.

```bash
git clone https://github.com/glebushnik/banschik_bot.git
cd banschik_bot
python3 scripts/setup_env.py
```

Заполнить в `.env`:

```dotenv
TELEGRAM_BOT_TOKEN=токен_из_BotFather
LLM_API_KEY=ключ_OpenRouter
ALLOWED_CHAT_IDS=-1001234567890
LLM_MODEL=google/gemini-2.5-flash
```

Модель должна поддерживать tool calling. `LLM_BASE_URL` можно заменить адресом
другого OpenAI-совместимого API. Векторизация от этого API не зависит.

```bash
docker compose build
docker compose run --rm --no-deps bot download-model
docker compose up -d
docker compose logs -f bot
```

Первая команда `download-model` скачает примерно 140 МБ модели и токенизатора в
постоянный том. Последующие расчёты выполняются локально без запросов к API эмбеддингов.
Без предварительного скачивания модель загрузится при первом индексировании.

### Подключение группы

1. Создать бота через `@BotFather` командой `/newbot`.
2. Отключить Group Privacy через `/setprivacy`, чтобы бот получал весь поток сообщений.
3. Добавить бота в группу. Если настройка privacy изменена после добавления, удалить
   и заново добавить бота. Права администратора для обычного чтения не требуются.
4. Указать числовой ID группы в `ALLOWED_CHAT_IDS`. Можно перечислить несколько через запятую.
   Если ID неизвестен, добавить бота и отправить сообщение: ID непрописанной группы появится
   в журнале `Ignoring group outside allowlist`. Её сообщения при этом не сохраняются.
5. Перезапустить бота после изменения `.env`: `docker compose up -d --force-recreate bot`.
6. Написать `@имя_бота что мы решили насчёт субботы?`.

Обычные сообщения, личные чаты, reply без упоминания и правки сообщений не вызывают ответ.
Только новые сообщения с явным упоминанием в тексте или подписи к медиа создают задание
для LLM. На одно только `@имя_бота` бот ответит приветствием. Между вызовами в одной
группе по умолчанию действует пауза 5 секунд; в течение неё новые сообщения сохраняются,
но дополнительные ответы не ставятся в очередь. Настройка: `REPLY_COOLDOWN_SECONDS=0`
отключает паузу.

Старая история до подключения не импортируется автоматически. Фото, видео, документы
и голосовые сохраняются как метаданные/file_id с текстовыми подписями; скачивания файлов,
OCR и распознавания речи в этой версии нет. Удаление сообщений в обычной группе Bot API
не сообщает: локальная копия удалённого сообщения останется. Правки доставленных сообщений
обновляют локальный текст и заменяют его чанки.

## Запуск Python без Docker для самого бота

Python 3.11+; на Linux для FAISS/ONNX может понадобиться пакет `libgomp1`.
Зависимости зафиксированы в `uv.lock`.

```bash
uv sync --frozen --extra dev
python3 scripts/setup_env.py
# Заполнить .env
docker compose up -d searxng
uv run --no-sync banschik download-model
uv run --no-sync banschik run
```

SearXNG доступен локально на `127.0.0.1:8080`; в контейнере бота используется
`http://searxng:8080`. Поиск можно отключить: `WEB_SEARCH_ENABLED=false`.

SearXNG работает на своей машине, но обращается к внешним поисковым системам.
Внешней LLM передаются вопрос и отобранные фрагменты переписки. Веб-поиск возвращает
заголовки, ссылки и фрагменты выдачи, а не полные страницы. Доступность результатов
зависит от поисковых систем и IP сервера; при сбое инструмент возвращает явную ошибку.

## Системный промпт

Файл [prompts/system.txt](prompts/system.txt) задаёт характер, язык, правила работы
с историей и поиском. По умолчанию бот дружелюбный, отвечает кратко и не использует
смайлики и эмодзи. Изменить файл и перезапустить бота:

```bash
docker compose restart bot
```

Для другого файла задать `SYSTEM_PROMPT_FILE`. `.env` и сам промпт модель не получает
как файлы: передаётся только содержимое системного промпта, без ключей конфигурации.

## Бэкапы

Встроенный APScheduler использует cron-триггер: ежедневно в **03:00 Europe/Moscow**.
Час, минута и зона задаются `BACKUP_HOUR`, `BACKUP_MINUTE`, `BACKUP_TIMEZONE`.
Внешний cron не требуется; контейнер должен работать. Если бот запущен после времени
бэкапа и сегодняшнего снимка нет, он создаётся при старте.

Архив `banschik-YYYY-MM-DD.tar.gz` содержит:

- `memory.sqlite3` — согласованный снимок SQLite через backup API, включая векторы и очередь;
- `indexes/*.faiss` — соответствующие индексы групп;
- `manifest.json` — время снимка, параметры эмбеддингов и SHA-256 файлов.

По умолчанию остаются снимки за сегодня и два предыдущих календарных дня в указанной
часовой зоне. После успешного создания и проверки нового архива более старые снимки
удаляются. Чужие файлы в каталоге не затрагиваются. Повторный бэкап за тот же день
атомарно заменяет предыдущий. При сбое создания старые копии не удаляются.

Модели, токены и `.env` в архив не входят. Бэкапы хранятся локально в отдельном Docker-томе;
для защиты от потери всего сервера нужно дополнительно копировать их на другую машину.

### Ручной бэкап и восстановление в Docker

CLI-команды, открывающие рабочую БД, требуют остановить процесс бота: файловая блокировка
защищает от двух одновременно запущенных экземпляров. Плановый бэкап делает работающий бот.

```bash
docker compose stop bot
docker compose run --rm --no-deps bot backup
docker compose run --rm --no-deps bot verify-backup /app/backups/banschik-2026-11-16.tar.gz
docker compose start bot
```

Восстановление сначала производится в **новый пустой каталог**:

```bash
docker compose stop bot
docker compose run --rm --no-deps bot restore /app/backups/banschik-2026-11-16.tar.gz --to /app/data/restored
```

Затем переместить исходные `memory.sqlite3`, `memory.sqlite3-wal`, `memory.sqlite3-shm`
(если существуют) и `indexes/` в отдельный каталог, а содержимое `restored/` — в `/app/data/`.
Можно также оставить файлы в `restored/` и изменить `DATA_DIR` контейнера на
`/app/data/restored` в `compose.yaml`; `MODEL_CACHE_DIR` оставить прежним. Запускать
восстановленную БД следует с теми же `EMBEDDING_MODEL`, `CHUNK_SIZE`, `CHUNK_OVERLAP`.

При локальном запуске:

```bash
uv run --no-sync banschik backup
uv run --no-sync banschik verify-backup backups/banschik-2026-11-16.tar.gz
uv run --no-sync banschik restore backups/banschik-2026-11-16.tar.gz --to ./restored-data
DATA_DIR=./restored-data uv run --no-sync banschik run
```

## Устройство памяти и скорость

Приём Telegram отделён от вызовов LLM и векторизации. Сообщение и offset сохраняются
в одной транзакции до подтверждения Telegram; ответ ставится в локальную очередь.
Фоновый worker раз в 2 секунды забирает пачку до 16 сообщений. Эмбеддинги и FAISS
работают в потоках, не блокируя сетевой event loop. Одновременно обслуживаются до
двух групп; внутри группы ответы выполняются последовательно.

SQLite — источник истины. FAISS использует нормализованные векторы и cosine similarity
через `IndexFlatIP` с явными ID чанков. После рестарта индексы восстанавливаются из
сохранённых в SQLite векторов; повторного вызова модели эмбеддингов не требуется.
Копии `.faiss` обновляются атомарно примерно раз в 30 секунд и входят в бэкап.
Устаревшие чанки после правки исключаются из поиска до завершения переиндексации.

Для небольших групп разумная начальная конфигурация: **2 vCPU, 4 ГБ RAM, 20–30 ГБ SSD**
на бота и SearXNG. GPU не нужен. Это ориентир, не результат нагрузочного теста.
Один миллион векторов размерности 384 — примерно 1.54 ГБ только под векторы FAISS;
их копия также хранится в SQLite. Реальная скорость ответа зависит прежде всего от API LLM.

Если поменять модель или параметры чанков, бот откажется смешивать несовместимые векторы.
Остановить бота, обновить `.env`, затем пересчитать память:

```bash
docker compose stop bot
docker compose run --rm --no-deps bot reindex
docker compose up -d bot
```

`reindex` сохраняет исходную переписку, удаляет старые чанки и считает новые.
При прерывании незавершённые сообщения обработаются после запуска.

Очередь восстанавливается после перезапуска; задания старше шести часов не выполняются.
Ответ может дублироваться, если процесс упал ровно после отправки Telegram, но до отметки
задания как выполненного: Bot API не предоставляет идемпотентный ключ для `sendMessage`.

## Проверки

```bash
uv sync --frozen --extra dev
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync pytest
```

Тесты работают без Telegram/OpenRouter-ключей и без скачивания модели: используют
настоящие SQLite/FAISS, маленький детерминированный embedder и HTTP-заглушки.
Проверяются упоминания с UTF-16 offset, тишина при обычных сообщениях, правки и
изоляция групп, цикл tool calling, ротация бэкапов, восстановление и повреждённые архивы.
Для проверки самой локальной ONNX-модели выполнить `banschik download-model`.
